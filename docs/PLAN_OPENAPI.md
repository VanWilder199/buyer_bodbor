# PLAN_OPENAPI.md — Контракт через задеплоенный бэк (вариант C)

> Цель: фронты генерируют TypeScript-типы из OpenAPI-спецификации **без запущенного локального бэкенда**.
> Репозитории раздельные (бэк и каждый фронт — отдельные GitHub-репо), поэтому контракт доставляется **с задеплоенного бэка по URL**.

## Принцип (почему именно так)

Фронт **не знает про бэк** и не ходит на `localhost:8080`. Он генерит типы прямо из URL задеплоенного `/v3/api-docs`. Закоммиченный JSON и pre-commit хук — гигиена бэка, на фронт не влияют.

### Плюсы / минусы выбора «задеплоенный бэк» (вариант C вместо npm-пакета или копии во фронт-репо)

**Плюсы**
- Один источник правды — спецификация всегда ровно того, что реально работает в проде.
- Ноль тулинга на доставку: не нужны пакетный registry, токены, синхронизация копий.
- Фронт переезжает на новую версию контракта автоматически после редеплоя бэка.

**Минусы**
- Фронт-сборка/типы зависят от того, что бэк **задеплоен и доступен по сети**. Если бэк упал — генерация типов в CI упадёт.
- Типы отражают **задеплоенную** версию, а не последний коммит бэка: поменял эндпоинт, но не редеплоил → фронт получит старые типы. Для пет-проекта это приемлемо, но надо помнить: API-изменение → сначала редеплой.
- Нет явного версионирования контракта (в отличие от npm-пакета с версией).

## Часть 1 (обязательно) — Бэк: отдать спецификацию наружу

### 1.1. springdoc в `build.gradle`

```groovy
implementation 'org.springdoc:springdoc-openapi-starter-webmvc-ui:2.8.x'
```

**Почему:** springdoc генерит OpenAPI-спецификацию прямо из Spring-контекста (контроллеров и DTO) в рантайме. Это значит, что задеплоенный бэк сам отдаёт `/v3/api-docs` — ничего коммитить или генерить заранее не надо.

**Почему версия 2.8.x:** линейка 2.7 рассчитана на Spring Boot 3.4, для 3.5.7 нужна 2.8. Точную последнюю минорку проверь на Maven Central. (Тривиальный выбор — без плюсов/минусов, просто факт.)

### 1.2. Открыть доступ в `SecurityConfig` (defaultChain)

Добавить после `.requestMatchers("/webhooks/**").permitAll()`:

```java
.requestMatchers("/v3/api-docs/**", "/swagger-ui/**", "/swagger-ui.html").permitAll()
```

**Почему:** сейчас `defaultChain` закрывает всё через `.anyRequest().authenticated()` — `/v3/api-docs` попадёт туда и вернёт 401. Фронт не сможет его скачать без токена.

**Плюсы / минусы** (сложное место — безопасность)
- Плюсы: фронт и Swagger UI работают без аутентификации; просто.
- Минусы: спецификация публично видна любому (структура API, имена полей). Для пет-проекта обычно ок, но это осознанный выбор.
- Если захочешь закрыть позже: обернуть в `@Profile("local")` или повесить basic-auth на эти пути в prod-профиле. Для MVP достаточно `permitAll`.

### 1.3. Проверить локально

- подними БД: `docker-compose up -d postgres`
- `./gradlew bootRun`
- браузер: `http://localhost:8080/v3/api-docs` → JSON, и `/swagger-ui.html`

**Почему:** убедиться, что спецификация реально отдаётся и видна, прежде чем тратить время на деплой.

### 1.4. Задеплоить бэк на стабильный URL (Render/Railway/Fly)

Проверка: `curl https://<url>/v3/api-docs` → 200 + JSON.

**Почему:** URL из этого шага — единственное, что нужно фронту. Дальше на бэке больше ничего делать не требуется.

✅ После 1.4 бэк уже «кормит» фронт.

## Часть 2 (обязательно) — Фронт: типы из URL

### 2.1. Установить `openapi-typescript` в каждом фронт-репо

```bash
npm i -D openapi-typescript
```

### 2.2. Скрипт в `package.json`

```json
"scripts": {
  "generate-types": "openapi-typescript https://<url>/v3/api-docs -o src/generated.ts"
}
```

Запуск: `npm run generate-types` → появится `src/generated.ts`.

**Почему:** `openapi-typescript` умеет читать URL напрямую — `curl` не нужен. Разработчик получает типы одной командой, локальный бэк не требуется.

### 2.3. Заменить ручные типы на сгенерированные

```ts
import type { components } from './generated';
export type ReportMediaDto = components['schemas']['ReportMediaDto'];
```

**Почему:** один источник типов вместо ручных `types.ts`, которые легко рассинхронизировать с бэком.

### 2.4. CI фронта (GitHub Actions, `.github/workflows/*.yml`)

Перед `typecheck`/`build`:

```yaml
- run: npm run generate-types
- run: npm run typecheck   # или build
```

**Плюсы / минусы** (сложное место — цепочка зависимостей в CI)
- Плюсы: типы всегда свежие (тянутся из задеплоенного бэка), бэк не нужен в раннере.
- Минусы: шаг `generate-types` требует, чтобы URL бэка был доступен **из CI**. Если бэк ещё не задеплоен или упал — сборка фронта падает. Локально (шаг 2.2) можно работать без сети к бэку только если URL доступен; в офлайне `npm run generate-types` не сработает (качает с сети).
- Замечание: если фронт должен собираться даже при недоступном бэке, придётся хранить закоммиченную копию `generated.ts` — это уже вариант B, со своими плюсами/минусами (см. Часть 3).

## Часть 3 (опционально, гигиена бэка) — не нужно для работы фронта

### 3.1. Группы + security-схемы — `OpenApiConfig.java`

Пути сверить с реальными контроллерами:
- inspector: `/inspector/**`
- admin: `/admin/**`
- buyer: `/auth/**`, `/cars/**`, `/purchases/**`, `/reports/**` (а не только `/reports/view` — `ReportAccessController` мапится на `/reports`)

**Плюсы / минусы** (сложное место — группировка спецификации)
- Плюсы: каждый фронт получает только «свои» эндпоинты, не тащит чужие; можно вешать разные security-схемы (Bearer для админа, X-Telegram-Data для инспектора).
- Минусы: при множестве групп фронту надо знать, из какой группы тянуть (`/v3/api-docs/admin`, `/v3/api-docs/buyer`…); лишняя конфигурация, которую легко переусложнить.
- Если групп не нужно — можно не делать, единый `/v3/api-docs` уже работает.

### 3.2. `@Schema(requiredMode = REQUIRED)` на DTO

**Почему:** springdoc по умолчанию считает поля опциональными, пока нет `@NotNull` или `@Schema(requiredMode = REQUIRED)`. Иначе в TS появится `field?: string` вместо `field: string`. Тривиально — без плюсов/минусов, просто проставь на ключевых DTO.

### 3.3. Закоммитить `openapi.json` + drift-проверка в CI

**Плюсы / минусы** (сложное место — два источника правды)
- Плюсы: снапшот спецификации в репо; CI может падать, если DTO изменились, а JSON не перегенерили (`git diff --exit-code`).
- Минусы: при варианте C фронт этот JSON **не читает** (он читает живой бэк) → ценность для фронта нулевая. Это гигиена «для себя» и для Swagger-документации. Есть риск захламить репо бесполезным артефактом.

### 3.4. Pre-commit хук

**Почему:** чтобы `openapi.json` (если решишь его хранить, п. 3.3) не протухал в бэк-репо.

**Плюсы / минусы** (сложное место — хук на каждый коммит)
- Плюсы: быстрый фидбек, спецификация всегда актуальна в коммите, который её меняет.
- Минусы: генерации нужен Docker/БД в момент коммита (если нет — хук должен мягко пропускать, а не блокировать); хуки по умолчанию не шарятся между людьми (`core.hooksPath`); на каждый API-коммит добавляется 30–60 сек.
- Вывод: хук — удобство, но настоящая страховка — drift-проверка в CI (п. 3.3). При варианте C хук вообще не влияет на фронт.

## Порядок и проверочные точки

1. **Часть 1** (бэк): springdoc → permitAll → проверить локально → задеплоить. Точка: `curl https://<url>/v3/api-docs` → 200.
2. **Часть 2** (фронт): openapi-typescript → скрипт → заменить типы → CI. Точка: `npm run generate-types` → появился `src/generated.ts`.
3. **Часть 3** (опционально): группы, `@Schema`, снапшот JSON, хук — только если нужно.

> Ключевое напоминание: API-изменение на бэке → **сначала редеплой**, иначе фронт получит старые типы.
