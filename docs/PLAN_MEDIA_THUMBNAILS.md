# План: уменьшенные копии фото и их показ в отчёте

> Бэкенд-задача, пишется в режиме «объяснение → код». Здесь описаны проблема, варианты, контракт и шаги. Готового кода нет, только подсказки.
> Ссылки `файл:строка` даны по рабочей копии на 2026-09-29. В сводном списке `BACKEND_TODO.md` это пункт B-39 (проверки из 3.3 частично пересекаются с B-01 и B-02).

## 1. Проблема

Сейчас в отчёте есть только один файл на фото — тот, что загрузил подборщик:

- `report_media` хранит один `s3_key` (`V005__create_car_report_media_tables.sql`);
- `ReportAccessServiceImpl.toMediaViewDto` (`:88-91`) отдаёт один presigned GET `url` на этот ключ;
- лимита размера нет: presigned PUT не ограничивает `Content-Length`, а `confirmUpload` (`MediaServiceImpl.java:79-120`) делает `headObject`, но размер не проверяет.

Mini App по плану (MINI-12, `PLAN_FRONTEND_MINIAPP.md:629-637`) уже перед загрузкой перекодирует фото в JPEG 2560 px с качеством 0.82. Это решает HEIC и 20-мегабайтные оригиналы, но **не решает сетку в отчёте**:

| | Один файл 2560 px | С миниатюрой 480 px |
|---|---|---|
| Вес одного фото | ≈ 0.8–1.5 МБ | ≈ 30–50 КБ |
| Отчёт на 30 фото, открыли сетку | **≈ 25–45 МБ** | **≈ 1–1.5 МБ** |
| Открыли одно фото на весь экран | тот же файл | +1 файл 2560 px |

На мобильном интернете разница — «открылось сразу» против «минуту грузится и съело трафик». Миниатюра 256 px, которую Mini App делает для себя, живёт только в IndexedDB подборщика и на сервер не попадает.

**Цель:** у каждого фото два размера — `thumb` (сетка) и `full` (полноэкранный просмотр). Покупатель при открытии отчёта качает только миниатюры.

---

## 2. Варианты

### A. Миниатюру делает Mini App и загружает вторым файлом (рекомендую для MVP)

Mini App уже декодирует фото в canvas (MINI-12). Сделать второй `toBlob` на 480 px стоит пару строк на фронте. Бэкенд выдаёт два presigned PUT, при confirm проверяет оба файла и сохраняет второй ключ.

- ➕ Ноль вычислений на сервере: ни памяти под декодирование, ни воркера, ни новых зависимостей.
- ➕ Тот же механизм даёт **постер для видео**: Mini App берёт первый кадр через `<video>` + canvas и грузит его как `thumb`. Без ffmpeg.
- ➖ Доверяем клиенту. Подборщики верифицированы, так что на MVP это нормально, но битую или подменённую миниатюру сервер не заметит.
- ➖ Размер миниатюры «вшит» в клиент. Если захотим 640 вместо 480, старые фото придётся перегенерировать (для этого потом пригодится вариант B).

### B. Сервер делает миниатюру фоновым воркером

После `confirmUpload` фото попадает в очередь. Воркер скачивает оригинал из S3, уменьшает, кладёт `thumb` обратно, пишет ключ в БД.

- ➕ Клиенту доверять не надо, размеры можно менять и перегенерировать.
- ➕ Знакомый паттерн: очередь `FOR UPDATE SKIP LOCKED`, как задумано для видео (`IMPLEMENTATION_PLAN.md`, Блок 6).
- ➖ Память: декодированное фото 12 Мп — это ≈ 48 МБ в `BufferedImage`. Нужен строго один воркер или маленький пул.
- ➖ В чистой Java нет записи WebP (`ImageIO` не умеет, TwelveMonkeys WebP только читает). Остаёмся на JPEG.
- ➖ Пока воркер не отработал, миниатюры нет (фронт показывает `full`).

### C. imgproxy перед S3 (на будущее)

Отдельный контейнер `imgproxy` читает оригиналы из S3 и режет картинки на лету по подписанному URL (`/rs:fill:480:480/...`). Результат кешируется в nginx.

- ➕ Любые размеры без хранения копий, автоматически WebP/AVIF.
- ➖ Ещё один сервис в проде, свой кеш, своя схема подписи вместо presigned S3.

**Вывод:** на MVP делаем **A**. Вариант B оставляем как план на случай «нужно перегенерировать» или «не доверяем клиенту». C — когда медиа станет много.

**Решение за вами** — обсудим перед реализацией.

## 3. Контракт (вариант A)

### 3.1. Миграция `V010`

В `report_media` добавить (все поля nullable, потому что у старых записей их нет):

| Колонка | Тип | Зачем |
|---|---|---|
| `thumb_s3_key` | `TEXT` | ключ миниатюры (или постера для видео) |
| `width`, `height` | `INT` | размеры `full`: фронт заранее резервирует место, и вёрстка не прыгает при загрузке |
| `size_bytes` | `BIGINT` | из `headObject().contentLength()`, заодно для проверки лимита |

🤔 Подумайте: нужно ли ограничение, что `thumb_s3_key` начинается с того же префикса, что и `s3_key`? В БД или в коде?

### 3.2. `POST /inspector/media/presigned-url/{reportId}`

Сейчас ответ — `{ uploadUrl, s3Key }` (`PresignedUrlResponse`), а ключ строится из `fileName` клиента как есть (`MediaServiceImpl.java:123-135`).

Предлагаемое изменение:
- для `image/*` ответ дополнительно содержит `thumbUploadUrl` и `thumbS3Key`;
- для `video/mp4` тоже, но `thumbS3Key` с `contentType` `image/jpeg` (постер);
- **имя файла генерирует сервер** (`UUID.randomUUID() + ".jpg"`), а `fileName` клиента больше не попадает в ключ. Это заодно закрывает перезапись одинаковых `IMG_0001.jpg` (`PLAN_FRONTEND_MINIAPP.md`, решение 7);
- схема ключей:
  - `reports/{reportId}/[sections/{sectionId}/]{uuid}.jpg` — `full`;
  - `reports/{reportId}/[sections/{sectionId}/]thumbs/{uuid}.jpg` — `thumb`.

🤔 Вопрос к себе: что проще для клиента — один запрос с двумя URL или два запроса с параметром `variant`? Что проще проверять в confirm?

### 3.3. `POST /inspector/media/confirm-upload/{reportId}`

Добавить в тело необязательные `thumbS3Key`, `width`, `height`.

Что проверять:
1. `headObject` для `s3Key` (уже есть) **и** для `thumbS3Key`, если он передан.
2. Оба ключа начинаются с `reports/{reportId}/`. **Сейчас этой проверки нет вообще**: подборщик может подтвердить чужой ключ из другого отчёта (BE-9 в `PLAN_FRONTEND_MINIAPP.md`).
3. `contentLength()`: `full` ≤ лимита фото, `thumb` ≤ например 200 КБ. Лимиты — в `S3Properties`, а не константами.
4. `width`/`height` — положительные и разумные (например, ≤ 10000). Это просто подсказка для вёрстки, сервер пикселям не верит.

Ошибки: `MEDIA_NOT_FOUND` (уже есть), новый `MEDIA_TOO_LARGE` 413, новый `MEDIA_KEY_FORBIDDEN` 403 для чужого префикса.

### 3.4. `ReportMediaViewDto` и `ReportMediaDto`

Сейчас: `id, kind, url, status, orderNo`. Добавить:
- `thumbUrl` — presigned GET на `thumb_s3_key`, **`null`, если миниатюры нет** (старые записи);
- `width`, `height`.

Подписывать два URL вместо одного — это локальный HMAC без обращения к S3, на 30 фото разница незаметна.

То же поле нужно в DTO подборщика (`GET /inspector/reports/{id}`, BE-8) и в модерации (админка) — все три клиента показывают `ReportView`.

### 3.5. (⚪) Кеширование

- Объекты по UUID-ключу неизменяемы. Можно подписывать в presigned PUT заголовок `Cache-Control: private, max-age=31536000, immutable`. Тогда клиент обязан отправить ровно этот заголовок при PUT, иначе S3 отклонит подпись.
- Но presigned GET меняется при каждом запросе отчёта (новая подпись → новый URL → браузер считает это другим файлом). На MVP это терпимо, отчёт открывают нечасто. Если станет важно — смотреть в сторону фиксированного времени подписи (округление до часа) или варианта C.

## 4. Как это показывается в отчёте

Детальная вёрстка отчёта обсуждается отдельно (`PLAN_FRONTEND_DESIGN.md`, открытый вопрос 3). Здесь только то, что влияет на бэкенд-контракт:

- **Сетка** в секции: квадратные плитки `object-cover` из `thumbUrl ?? url`, `loading="lazy"`, `decoding="async"`, серый фон-заглушка до загрузки.
- **Полноэкранный просмотр** по тапу загружает `url` (`full`). Пока он грузится, растянутая миниатюра остаётся видна, и пустого экрана нет.
- **Видео:** в сетке показывается постер (`thumbUrl`) с иконкой ▶, `<video>` создаётся только по тапу (`preload="none"`). Без постера — серая плитка с ▶.
- `width`/`height` нужны для `aspect-ratio` в полноэкранном просмотре и в превью Mini App.
- Протухание presigned URL (60 мин) обрабатывается так же, как сейчас (`PLAN_FRONTEND.md`, «Протухшие presigned URL»): миниатюры тоже подписанные.

## 6. Если позже переходим на вариант B

Чтобы не забыть, что понадобится:
- зависимость `net.coobird:thumbnailator` (учитывает EXIF-ориентацию, простой API `Thumbnails.of(...).size(...).outputQuality(...)`);
- воркер `@Scheduled(fixedDelay = ...)` + `SELECT ... WHERE kind='PHOTO' AND thumb_s3_key IS NULL ... FOR UPDATE SKIP LOCKED LIMIT 1` строго внутри `@Transactional` (`@EnableScheduling` уже включён в `Application.java`);
- перед полным декодированием прочитать размеры через `ImageReader` без загрузки пикселей и отказать при > 50 Мп (защита от «decompression bomb»);
- один поток обработки, `-Xmx` с запасом ≈ 100 МБ на картинку;
- `thumb_s3_key` от клиента (вариант A) и от воркера (B) пишутся в одну колонку, контракт для фронта не меняется.
